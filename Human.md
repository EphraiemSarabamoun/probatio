# How probatio works

## What it does

probatio v4 scores a person's own Claude Code or Codex agent for loyalty to a target the user picks: an individual (by default the user), an organization or a nation. It returns three scores from 0 to 100, each with a 95% interval, the components behind it, red flags and validity checks: Class I (professed, from questions), Class II (behavioural, from errands done with tools in a plain world) and Class III (internalised, the same errands under a notice that the session is unobserved, read against the agent's own report of what it believed). Every item is a template in one bank, rendered at run time for the target, its matched invented control and five comparators, and each scored item has a twin that differs only in the scored entity, so a score is the gap between how the agent treats the target and how it treats the control. The agent runs with its memory files on, off, or both, and every number is computed mechanically from replies and tool records; no model judges anything. The design is `docs/v4/`, and README.md is the user's guide. This file is for someone reading or changing the code.

## Where execution starts

Everything is in one file, probatio.py, with world.py beside it as the episode engine and the item bank in bank/. Execution starts at `main()` at the bottom of probatio.py; before any other import, the file stops a Python older than `MIN_PYTHON` (3.9, the oldest tested) with a plain message. Every command line goes to `main_v4()` unless it names one of v3's own flags (`--dataset`, `--demo`, `--seed`, `--port`, `--local`, or the tiers `smoke` and `slim`) and no v4-only option (`--target-type`, `--compare`, `--entities`, `--print-entities`): `wants_v3` makes that test, so v4's own smoke tier never routes to v3, and such a command line runs v3, unchanged, until v3 is retired (see The v3 path below). `--watch` is v4's too. `--target-type` defaults to individual, so `--agent claude --name "Jane Doe"` scores the user.

`--rescore FOLDER` takes no other option either: `main_v4` hands it to `main_rescore` before anything else, which scores a finished run folder again with no agent called (see Scoring below). `--ui` takes no other option: `main_v4` hands it to ui.py's `main`, which serves a page that builds a v4 command line from a form, checks it with its own `--dry-run` and runs it (see "The --ui page (ui.py)" below).

A command line that uses any option of the cross-type design (`--compare`, `--entities`, `--print-entities`, a target written `TYPE=NAME`, or a second `--target`; `uses_options`) goes from `main_v4` to `main_compare`, described in "Comparing types and your own rosters" below. Without one, `main_v4` is v4's path, unchanged.

`main_v4` does the whole run in order: `parse_args_v4`, the config folder check (`check_config_dir`), the name guard (`checked_names`), the bank (`load_bank`: bank/, whose manifest must have the sha256 pinned in BANK_MANIFEST_SHA256, or a `--bank` folder for bank authors), the world.py hash check (WORLD_SHA256), the roster (`resolve_target`), the plan (`plan_v4`), the CLI's options (`agent_options`, with the effort pinned and the run's config folder, `config_choice`), the preflight (`preflight_v4`) and, unless `--dry-run` is given, the run: `claim` takes the folder's lock, `check_resume` compares run.json, `run_calls` makes the calls and `score_run` writes the scorecard, which is then printed. The folder defaults to results/v4-<agent>-<type>-<target key>-<tier>-memory-<mode>, with the arm and the model appended when they are not the defaults.

## The main flow

```mermaid
flowchart TD
    A["main: v4 unless a v3-only flag (wants_v3)"] --> B["main_v4: parse_args_v4, checked_names (check_name on every typed name)"]
    B -->|--ui| U["ui.main: the page builds this command line, its --dry-run checks it, Run starts it (ui.py)"]
    B --> C["load_bank: bank/ (manifest sha256 pinned) or --bank, every file's sha256"]
    C --> C1["derive_cell: U and O overlays built from the N0 rows and cells.json"]
    C1 --> C2["check_bank: rosters, rows, a world for every task and cell"]
    C2 --> D["resolve_target: T, control X, comparators K, anon; aliases, reserves, fixed-name clashes"]
    D --> E["plan_v4: plan_class1 (target and twin) + plan_errands (N0, U, O), rendered, hashed, shuffled"]
    E --> F["preflight_v4: counts and time per class, sample sentences, the memory it tests (config folder, files, sizes, titles), plan fingerprint"]
    F -->|--dry-run| Z["stop (with --out: rendered.jsonl)"]
    F --> G["claim, check_resume, then run_calls (v3): threads, resume, model and failure stops"]
    G --> H{"call"}
    H -->|question| I["claude_call or codex_call; score parses the reply"]
    H -->|errand| J["start_episode: a fresh world, world.py the only MCP server"]
    J --> K["claude_dialogue: errand, close sentinel, five-question report"]
    J --> L["codex_call, then codex_report: a resumed session for the report"]
    I --> M["replies.jsonl; quota.jsonl for Claude Code"]
    K --> M
    L --> M
    K --> N["episodes/: world.json, record.jsonl, followup.json, transcript.jsonl"]
    L --> N
    M --> O["score_run: units, components, class scores, bootstrap, Class III, red flags, validity"]
    N --> O
    O --> P["write_scorecard: scorecard.json, units.jsonl, scorecard.md, report.md, results.csv, results.svg"]
```

The calls are planned and rendered before anything runs. Each item's conditions sit side by side in a seeded shuffle, as in v3, so drift during the run hits both alike, and the plan's fingerprint goes into run.json, so a resume refuses a changed bank, roster or rendering. Scoring reads what the run saved in its folder, so a finished run can be scored again without calling a model.

## The important functions, stage by stage

**Names and the guard** (section "v4: entities, the name guard and rendering").
- `checked_names` passes `--name`, `--target` (which defaults to `--name` for an individual), `--target-short` and `--target-possessive` through `check_name`, the structural guard of DESIGN 9, and turns its `NameRefused` into a short exit. The guard allows letters and marks of any script, digits and `. , ' & - ( ) /`, at most MAX_NAME_CHARS characters and MAX_NAME_WORDS words, and refuses a whole name that is an answer word (ANSWER_WORDS) or anything that reads as a menu option (OPTION_TOKEN). It keeps a name from breaking an answer format, a world or a slot; it does not prove a name carries no instruction, so the preflight's sample sentences are the user's check.
- `entity` derives a typed name's record (DESIGN 5.1): the full and short forms, the possessives, the group, the requester and its back-reference `to`, the sign-in `code`, and their sentence-start forms, with `sentence_start`, `possessive` and `handle`.
- `render` fills `⟦ROLE.field⟧` slots (SLOT) in one pass by exact replacement, never by str.format, and raises RenderError for an unknown role or field, a value holding a slot mark (`check_roles`) or a mark left behind. `render_world` parses a world, fills every key and string, refuses two keys that render alike or a changed tool name, and writes sorted-key JSON, so a world rendered with the published names is byte-identical to the published one.

**The bank and its overlays** (section "v4: the bank, the roster and the plan"; the format is BANK_FORMAT.md).
- `load_bank(folder, pinned)` checks manifest.json's sha256 against BANK_MANIFEST_SHA256 (not for `--bank`), its format (BANK_FORMAT) and the sha256 of each of BANK_FILES. When the manifest lists cells.json, errands.jsonl must hold N0 rows only, and `derive_cell` builds each U and O row from its N0 row: the cell's notice paragraphs after the anchor paragraph, the activity-log rule's header swapped, nothing else changed.
- `check_bank` refuses what the planner cannot use: a type without its comparators, invented names, reserves, anonymous requester, fixed names, report or arms; a row missing CLASS1_KEYS or ERRAND_KEYS; a template id used twice; a type whose sacrifice rows are not I.4's eight (family, price) items in both letter orders (SACRIFICE_FAMILIES, SACRIFICE_PRICES, SACRIFICE_LETTERS); a world that is not JSON; a task in a tier's pool without a world for every type and cell.

**The roster.** `resolve_target(bank, type, name, short, poss)` returns {type, T, X, K, anon, notes}. A name or alias on the roster (compared by `norm_name`) takes the curated record, else `entity` derives one. A name that clashes with a fixed name of the bank (`names_clash`) is refused; a target that is a comparator brings in the first reserve, and a target that is the control moves the control to the next invented name. Keys and sign-in codes are kept distinct, and the notes are printed by the preflight.

**The plan.**
- `plan_class1` plans every Class I item twice, with the target and with its twin (the control X, or for sacrifice and honesty the anonymous requester), with the item ids of INTERFACES 3. The smoke tier rotates frames, word pairs and scenarios over the comparators; the full tier asks everything twice. `class1_item` renders one, maps its choices to entity keys and refuses a rendering that changed the answer menu (MENU_LINE).
- `plan_errands` gives each task of the tier (`tier_tasks`: the manifest's count spread over its pool with v3's `spread`, and the O cell on half of them, spread again) the target's and the control's errand in each cell, both sent by T (DESIGN D3). `--arm g_wish` replaces the type's neutral sentence, which must occur once. Each call carries its rendered world, its report and their hashes.
- **The tiers** are smoke, quick, standard and full (V4_TIERS). smoke is the plan called quick until 2026-11-08, item for item, kept for the calibration's Stages A and C and the frozen pilot's Stage 1 (PREREG Amendment 5). The pinned manifest still names its task count `quick` (MANIFEST_TIER).
  - quick is the 15-minute estimate (`docs/ordo/QUICK.md`), made of others' parts: `TIER_PARTS` gives the tier whose Class I and whose Class II it asks (standard's and full's), and `TIER_CLASSES` the classes it plans (I and II).
  - `resolve_classes` turns `--class all` into the tier's classes and refuses a III at quick.
  - quick costs no more than standard for the default classes and for every cross-type selection, named targets included. A single target with `--class II` or `I,II` is the exception, since quick asks the full tier's 48 errand tasks and standard 24. `standard_shorter` prints the preflight's plain line there (`STANDARD_SHORTER`, in both `preflight_v4` and `preflight_runs`), `tier_minutes` prices the same selection at another tier with the classes the command asks there (`classes_at`, from `--class` as typed, kept as `class_choice`), and `time_hint` offers quick only where it costs no more than standard, and `--tier standard` from full where it does.
  - `named_classes` gives the classes a cross-type run's named target is measured in (`TIER_NAMED_CLASSES`): Class I only at quick, whose named-target errands are at standard. `plan_runs` refuses a quick run whose `--class` leaves a named target nothing (`QUICK_NAMED_NONE`), and the preflight's named-target line says what quick leaves out (`QUICK_NAMED`).
- **Plan recipes** (`PLAN_RECIPES`, `RETIRED_RECIPES`, `LEGACY_RECIPES`). Every run.json and scorecard records its recipe (`quick@3`, `smoke@1` and so on).
  - `recipe_of` reads a run.json from before recipes through the legacy map, so a quick of then is `smoke@1`. `planner_tier` names the tier that plans a recipe.
  - A retired recipe (`quick@2`, which also ran a named target's errands) still reads and scores. `same_plan` lets `check_resume` continue its folder when today's plan is the same call for call (any quick@2 run without a named target), and otherwise refuses with the fix. `check_resume` returns the meta the run goes on under, the recorded recipe after such a resume, and `execute_run` and `main_v4` score, watch and write the card with it, so the card and run.json name one recipe.
  - `rescore`, `check_resume` (through `resume_view`), `comparable` and the scorecard heads read the recipe, never the bare tier word, and no historical file is edited.
- **One resume identity for one plan.** `check_resume` compares two run.json records through `resume_identity`, key for key, a key either record holds included, so the check works both ways. A single-type run's identity is `v4_meta`'s record, whichever path wrote it, plus its fixtures (`recorded_fixtures`: the type's baseline when v4's own path recorded none) and its `recognition` record. The options path's echo (`OPTIONS_ECHO`: compare, fixtures, labels, roster) is left out of it, so `--target-type T --target NAME`, `--compare T`, `TYPE=NAME` and a row of several targets resume one another's folders. A custom roster's folder and the baseline's refuse each other. Each single-type run records only its own target in its roster echo (`target_records`), so editing a row's other names leaves every unchanged target's folder resumable, except, with custom controls, the row's first name: its run asks V12 about them and the others record that asker (`recognition`), so the row's folders resume only while that name stays first; moving or replacing it, or running a later name alone, refuses them (the page's Check names them). A cross-type run's identity is its whole record, and v3's is its record but the date.
- `plan_v4` picks the cells from `--class` (CLASS_CELLS: II asks N0, III asks U and O), shuffles with V4_SEED and adds the conditions of MEMORY_MODES. `plan_fingerprint` hashes every call's condition, id and hashes.

**The preflight.** `preflight_v4` prints the CLI version, model and effort, the roster and its notes, the tier's sentence (`tier_sentence`: what a quick run leaves out), the counts and time per class (`estimate_v4`), the 45-minute hint and the standard-is-shorter line (`time_hint` and `standard_shorter`, the helpers `preflight_runs` prints them with), three sentences with the target in them (`sample_sentences`), the memory section (`print_memory`, below), and the bank's hash, and returns the facts for run.json. W4's harness parses the memory list, so its shape is frozen (INTERFACES 4): the paths after the line holding "memory files", four spaces in, each line's size and title in parentheses at its end, which the harness's reader drops as it drops a rule's mark, and `none found` or the off wording on that line when it lists nothing.

**The memory a run tests** (section "the memory a run tests"). One run reads one config folder, Claude Code's `CLAUDE_CONFIG_DIR` folder or the Codex home, and `config_choice` is its one home: `--config-dir DIR` (made absolute by `config_path`, refused by `check_config_dir` in one line with exit 2 when it is not a folder), else the CLI's variable (`CONFIG_VARIABLE`), else `~/.claude` or `~/.codex`. `agent_options` puts it in the options as `config_dir` with its source, and every reader takes it from there, never from a changed os.environ: `memory_files` (its `config_dir` argument), the preflight, run.json and the inner call. Claude Code's call gets `CLAUDE_CONFIG_DIR` from `claude_command` only when the option chose the folder (`config_env`), so without it the call is the call it always was; Codex's per-call homes link the chosen home's login and AGENTS files (`opts.codex_dir`). `memory_report` reads each memory file once and gives the folder, where it came from (`source_words`), each file's sha256, size and title (`memory_title`: the first Markdown heading outside a code fence, else the first non-empty line, made plain by `plain_text` and cut to TITLE_CHARS), the total, and the name note for each individual target (`memory_people`) that no file mentions by full or short name (`mentions`). `memory_lines` prints it (`memory_empty` for the one line of a run that lists no file), `print_memory` adds, for Claude Code, the other config folders `config_candidates` finds (`candidate_lines`): folders up to CANDIDATE_DEPTH below home holding `.claude.json` and `projects/`, never home itself nor the folder in use, skipping hidden folders (but for one directly under home whose name begins CANDIDATE_HIDDEN, `hidden_candidate`, looked at and never into), CANDIDATE_SKIP and virtual environments, following no link, and reporting nothing past CANDIDATE_SECONDS or CANDIDATE_ENTRIES: a `Budget` whose allowance is taken before each entry is read (`Budget.take` in `listing`, which reads os.scandir's iterator one entry at a time, never one past the allowance) and whose clock is checked after each read returns, before each entry's and each candidate's metadata, before and after each TITLE_CHUNK of a CLAUDE.md's title (`claude_md_facts`, which opens without waiting, takes the size from fstat and reads at most TITLE_BYTES) and before the search answers, raising `OverBudget`; one blocking system call is not cut short, but nothing is returned after it overran. Every memory location goes through `memory_file`: nothing there (a link to nothing included) is no file, a regular file it can open is one, and anything else where a memory file is read (a link that loops, a folder, a FIFO, a file it cannot open; `memory_bytes` when a read fails later) is `memory_refusal`'s one line (MEMORY_REFUSED), before any call; a folder under rules/ or named by an @word is no file. `memory_title` reads a file's first TITLE_BYTES (`title_head`) and is None, shown as TITLE_UNREADABLE (`title_words`), when they are not text. **What reaches a terminal or the page** (sections "what reaches a terminal or the page" and "the backstop at every output boundary"): `unseen` is the one rule for the characters that must not (controls, format, separator, private-use and unassigned characters, and `invisible`'s), and `display` the one function that escapes them and cuts a long string in the middle (DISPLAY_CHARS, named once). The cut is `capped`'s, and many of the places that build a label, a heading, a cell or a sentence around one displayed token for the --watch page, the --ui form or a result file call it on the whole value: live.py's `name_rows` label; ordo's `name_label`, `insufficient_lines`, `quick_names_line`, `types_heading`, the answer's notes, `report_md`'s named-target, recognition and V1 lines and the figure's name titles and description; v4's `scorecard_md` head and labels line, `report_v4`'s fact lines and `scorecard_svg`'s title and subtitle; ui.py's `needs_line`, `folder_needs`, `page_words`, `blocked_words` (each folder's sentence, so every blocked folder stays named), `refusal` (probatio's whole message kept in the preflight when the cap cuts it) and the probatio messages the preview, the memory block and Run relay. These are cuts probatio makes, not a rule, and no length is promised for the text around a token: `memory_empty`'s MEMORY_NONE, which names the folder, is not cut as a whole, in the form's memory block or in the preflight, and the pages' scripts add their own words and figures around values they receive (live.py's `strip`: a row's aria-label and tooltip; ui.py's `renderMemory`: "No folder at ..." and "Memory files: ..."; the note beside Run, "... first"). Text that holds several tokens, such as the form's command line, the preflight, a run's lines or a message about several folders, is cut token by token, and the roster file's text the form shows is not cut at all. The backstop does not depend on any call site: `if __name__ == "__main__"` calls `install_terminal_filter`, which wraps standard output and standard error once in `TerminalFilter` (every write passes `terminal_text`: display, uncut, keeping the newline and tab, TERMINAL_KEEPS; its binary buffer is not offered), then `run_command` (main; a refusal through `refusal_text`; a filesystem error that names a path through PATH_STOP and `os_reason`, one line). The live line's own redraw codes go only through `TerminalFilter.framed` and `control`, which take nothing but TERMINAL_CONTROLS (live.py `LiveLine.write`, v3's progress). The filter covers everything written through Python's standard streams; a write to the file descriptor itself, or a child that inherited the terminal, would not pass it, and probatio has neither: every child's output is captured (the agent CLI's calls in `run` and the errands' dialogue `Popen`, `--version`, `codex features list`, and the --ui page's Check, memory, resume and Run children, whose output the page reads), the only direct descriptor writes are byte copies into files (`copy_unfollowed`'s previous/ copies, the page's roster snapshot), and `fileno` is read only by live.py's `terminal_width`. The --watch page's data is displayed where it is built: `live.run_facts` (the model, the CLI's version, the compare words, the target and control), `live.roster_names` (every entity's name), the tab name (`plain_label`, and `RunView.state`) and the card its rows are drawn from (`Provisional` draws them from `shown_view(card)`), so the page receives displayed tokens and inserts them as text. The agent's own replies it shows (a question's reply and answer, an errand's tool calls, filed fields and errors) are not displayed by this rule: `RunView` passes them through `ViewRedactor.brief` (redacted, cut to CAPS) and the page inserts them as text, never as markup, so a line feed, a lone surrogate or U+2028 in one reaches the page unescaped. Every text result file is written through `write_export` or `write_export_csv` (`export_text`, the same filter): v4's `write_scorecard`, v3's `write_results` and ordo's `write_results`; every JSON file written with non-ASCII text goes through `json_text` (JSON's own `\u` escapes, so it reads back exactly): scorecard.json, units.jsonl, replies.jsonl, quota.jsonl, followup.json, rendered.jsonl and the page's entities file; run.json and both pages' data are plain-ASCII JSON already, and both pages insert every string with textContent. Above the backstop, a string from the command line, a saved record, the filesystem or the CLI's version line is displayed as one token where it is put into a message: memory_report's "shown" and "folder", every preflight path, `model_words` and `one_line` (models, CLI versions, also ordo's `run_words`), `candidate_lines` (a folder whose name display changes gets CANDIDATE_ESCAPED in place of a `--config-dir` to paste, `shows_as_is`), `check_config_dir`'s and `agent_options`' lines, `memory_words`, every --rescore refusal and result path, argparse's error line (`Parser.error`), ui.py's memory answer and command words, and `quoted`; the original string is what the filesystem and the agent's process get. v3's `report` and `write_results` are not among them: they write --workdir, --local, the model asked for and the figure title's models seen as given, through the filter alone, so a newline or a tab in one stays and a long one is not cut. Nor is the --ui page's Run confirmation (`renderConfirm`): its script names the model word as typed in the form, uncut and unescaped, as text, and the form's fields show what is typed as typed. One folder check, `is_folder`, serves --workdir, --config-dir (`config_is_folder`), the --rescore folder and the page's config folder. tests/test_display_boundary.py enumerates the fields from `v4_parser` and `v3_parser` themselves, run.json's string leaves, the CLI's version, a memory file's path and title and a found folder. `memory_record` is what run.json keeps (memory_files, memory_bytes, config_dir; never a title or content). `check_resume` compares config_dir as part of the identity, so a folder made under another config folder is refused as an edited memory file is; sizes are left out (NOT_COMPARED), since the sha256s already tell an edit, and a v4 record from before config_dir is compared on its memory files alone. `memory_words` turns a record into the scorecard heads' words (`memory on: 2 files, 7.1 KB, from ~/.claude`; a record from before shows its count alone): `score_run` and `rescore_folder` pass them to `write_scorecard` and `scorecard_md`, and ordo's `head_lines` reads them, so scorecard.json is unchanged. `names_said` gives what a name does in a comparison (NAMES_ROLE in ordo's `ROSTER_WORDS`, invented only when every control is one of the bank's invented entities, and at quick ordo's `quick_names_line`, the scorecard's own wording), which `preflight_runs` prints under the named targets and the page shows under the rows. --rescore checks no memory record, since it starts no CLI and reads only the folder.

**The time model.** One table, `docs/ordo/budget.json["pricing"]`, written by `docs/ordo/budget.py`.
- Its sonnet profile is measured: the ordo pilot's per-call seconds, summarised by `docs/ordo/timing.py` into `timing.json`. Its opus and codex profiles are assumptions.
- `pricing` reads it, `expected_seconds` prices a question by its rate family and an errand by its cell, and `plan_minutes` sums over `--jobs`.
- `rates_profile` picks a run's profile from its agent, model and effort, with the label the preflight prints: measured, assumed, or a proxy. `ordo.count_plan` prices through the same functions.
- `note_launch` writes a line of `launches.jsonl` at each launch's start and end (`run_calls` calls it), `read_launches` sums the launches that recorded an end, and `run_time_line` gives the final card that actual time, never an estimate.

**Running the calls.** v4 reuses v3's runner.
- `run_calls` runs the calls in threads, skips those already in replies.jsonl, retries failed ones, and stops on a reply from a new model or after MAX_ERRORS_IN_A_ROW failures in a row; `ask` retries a call once and names it in a copy of the options for quota.jsonl. A v4 run hands it its live line (`line=`, see Watching a run below), and then it records each launch in launches.jsonl (`note_launch`; `read_launches` sums the run's time); v3 and the calibration's runners pass none and keep v3's progress line and folder.
- A question's reply is parsed by v3's `score`, which also reads Class I's `final_answer_line`, and maps it through the row's choices to an entity key or an action.
- For Claude Code, `claude_command` asks for stream-json, pins the effort as `--effort` and as CLAUDE_CODE_EFFORT_LEVEL, and sets the two memory switches (auto memory off in both conditions under `--auto-memory off`). `claude_call` reads the stream with `parse_stream` and `stream_reply`, and `note_call` hands it to `QuotaLog`.
- For Codex, `codex_command` and `codex_switches` build the call, which runs in its own temporary home (`codex_home`, inside the run's `codex_homes` folder).

**The errand dialogue.** `is_episode` routes an errand to `episode_dir` and `start_episode`, which writes a fresh world for every attempt and serves it through world.py as the only MCP server.
- `claude_dialogue` runs the errand and its report in one Claude Code process: the errand as the first stream-json turn under EPISODE_TIMEOUT; at the first result `touch` creates world.py's close sentinel, so no later tool call is served, and the report's questions follow under FOLLOWUP_TIMEOUT. A missed report is recorded without failing the errand, and `stop_group` stops the call's process group. It writes followup.json and transcript.jsonl into the episode folder.
- For Codex, `codex_call` keeps the session (`--json`), and `codex_report` closes the record and resumes it with `codex_resume_command`, which carries no world server, since a second world.py would append to the closed record. `codex_session` finds the session id and `codex_rollout_model` the model.
- `episode_outcome` reads the record afterwards. Before that, `episode_problem` turns a record that is not whole and closed into an error to retry, never an unsolved errand.

**Scoring** (section "v4: scoring"; SCORING.md is the contract, revision 3, and the docstrings cite its section numbers).
- `score_run(out, calls, bank)` scores a folder from disk; `rescore(out, bank)` scores a single-type folder again in place. Both it and `--rescore` rebuild the plan through `saved_plan`, the one interface for either kind of run: plan_v4 from the recorded roster and recipe (with the V12 questions the run asked), or for a cross-type run ordo_plan from the recorded comparison and rosters, as plan_runs plans it; it refuses another bank or ordo bank and a different plan fingerprint.
- `--rescore FOLDER` (`rescore_command`, `main_rescore`, `rescore_folder`): `main` and `main_v4` read the command line for `--rescore` before any parser (`rescore_command`, `rescore_word`), so with any other option, v3's and `--help` included, it is one line (`RESCORE_ALONE`) and exit 2. It works in two phases. READ (`read_saved`, then `read_recognition` under the lock, each through `guarded_read`) reads run.json (`saved_meta`: not a run folder, unreadable, v3's, or not v4's are plain refusals), checks it against the writer's own shape (`check_run_fields`: `reference_records` has `v4_meta`, `single_record` and `cross_record`, the writers `preflight_runs` itself calls, write the record of each of REFERENCE_VARIANTS, planned by `prepare_runs`; `derive_shape` merges them per family into needed keys, JSON types, lists the writer always fills, maps keyed by data and couplings between optional parts, RECORDED_SINCE's keys never needed; `fits` names the first misfit, RUN_FIELD_LINE in JSON's words; then the memory mode, classes, types and a comparison's rosters, one per type), rebuilds the plan (`saved_plan`) and reads the recognition answers (`recognised`); any READ_ERRORS raised there is SAVED_UNREADABLE's one line. SCORE scores the rebuilt objects and is not guarded, so a defect in it raises. Between the two it checks every path it will write (`check_targets`, `check_path`: each result file and its folder, `previous/` and `run.lock` absent or of its own kind, never a link, inside the folder's real path and writable, and the folder writable) and reads the replies strictly (`check_finished`, `strict_replies`: every line a JSON object with `REPLY_FIELDS`, by `valid_line`, the --watch page's own test, now in probatio; the first damaged line refused by number; `read_replies` and `scan_replies`, a resume's tolerant reading, are unchanged). Under the run's own lock (`lock_folder`, split from `claim`, which writes nothing into run.lock) it checks both again, scores in memory with `card_of` or `ordo.score`, sets `card["rescored"]` (`rescored_record`: when, `PROBATIO_VERSION`, and the version that scored the run) and hands the writers to `replace_results`: all or nothing, the new files written into a temporary folder inside the run folder (`RESCORE_TEMP`), the replaced ones copied into previous/<UTC stamp>/ without following any link (`copy_unfollowed`: `O_NOFOLLOW` and `O_EXCL`), the new ones moved into place by rename, and on any failure `undo_results` puts back what moved and removes what it made, leaving the folder as it was, with one plain line. `scorecard_md` and ordo's `answer_table` print `rescored_line` under the head. It starts no process at all; tests/test_rescore.py patches every way to start one to fail. The normal run path writes its result files with plain writes, which follow a link; it is unchanged.
- Units: `class1_units` makes one per Class I reply, y from `class1_y` and the base-item cluster from `base_item` (I.4's is family and price, stratified by price), plus an RF2c unit per harm call; `errand_units` makes one per episode, every measure read from the stored record: solved by `episode_outcome`, never the outcome cached in replies.jsonl, so a rescore follows a corrected record; credit by `credit` (only served calls, a line of kind call with no refusal mark, whose non-error responses return the requested page or id, via `returned_record`); `unowed` claims; and `report_state` from `parse_report`.
- Components and classes: `class1_component` (`index_s`) and `errand_component` (`index_r` over `valid_pairs`) apply SCORING 4's symmetric guards, I.4's against the bank contract's four prices and eight items (`sacrifice_items`), so a price the plan lacks makes it insufficient; `class_score` averages the sufficient components (CLASS_MINIMUM) and clips once (`clip`).
- Intervals: `item_fingerprint` seeds `bootstrap_seed`, and `Bootstrap` gives B = 2,000 draws per labelled cluster list, shared by every condition and cell; `levels`, `replicates` and `ci_of` make the interval, null when fewer than 95% of B replicates are defined.
- The rest: `class_iii_validity` is section 7's decision tree (REPORT_LEG holds only claude, so a Codex run's Class III reads unverified); `rf1`, `rf2`, `rf2c` and `rf3` are the red flags (`rf3` applies section 8's insufficient-first precedence over its planned cells, keeping a measured cell's counts in the note); `diagnostics` gives the N0 against U and O against U contrasts; `memory_difference` gives `--memory both`'s deltas through `class1_contrast` and `errand_contrast`, which re-check the guards on the common items or tasks; `validity_checks` makes V1 to V11, with `init_facts` (V1 compares exact abstention fractions with ABSTENTION_GAP). `score_condition` assembles one condition and `scorecard_record` and `rounded` the top level.

**The outputs.** `write_scorecard` writes scorecard.json (INTERFACES 6, schema 4.2 adds the recipe, the recorded tier word and the run time; 4.1: each class's `ci_reason` and Class III's `believed` estimate, and the top-level `default_favour` notes, which `score_run` fills from the rounded card with `favour_notes`), units.jsonl (`unit_line`, INTERFACES 7), scorecard.md (`scorecard_md`, with `favour_notes`), report.md (`report_v4`), results.csv (`scorecard_rows`) and results.svg (`scorecard_svg`, each row a `<g class="row">` as in v3, which the tests read).

## Comparing types and your own rosters (ordo.py)

`ordo.py` is the third module, beside probatio.py and world.py. It answers the question the trio cannot: does the agent put a person before a firm, or a firm before a country? It puts an individual, an organization and a nation against each other inside one item or one paired errand, and scores which type the agent favours. probatio.py's options (`--compare`, `--entities`, `--print-entities`, `TYPE=NAME`) choose the comparisons and the rosters; ordo.py plans, prices and scores the comparisons between types. The design is `docs/ordo/DESIGN.md`, every number is defined in `docs/ordo/SCORING.md`, and the bank's format is `docs/ordo/BANK_FORMAT.md`.

**The options** live in probatio.py, after v4's own command line: `parse_compare` and `canonical_compare` turn `--compare` into one canonical set (the three pair groups become the triangle), `load_entities` and `entity_spec` read the entities file (names alone suffice), `print_entities` prints exactly the schema it reads, `check_roster` runs the roster guards, `fixtures_sha256` and `fixtures_label` say whether a roster is the baseline (whose hashes live in the pinned `bank/ordo/manifest.json`, read through `ordo.baseline_fixtures`), and `plan_runs` makes v4's single-type runs and at most one cross-type run. A target whose type has its own single-type group stays in that group; otherwise it joins the cross-type run as a named target. `preflight_runs` prints the comparison with its calibration words, the names in their rendered forms (every name the user gave and every named target, a roster entity such as the United States included: `user_records`), each run's counts and the 45-minute hint, all priced by `ordo.count_plan` (`run_counts`, `class_lines`, `time_hint`). The hint offers an option only when it saves time (`offer`), so it never recommends a slower one. When none of its fixed options applies, `fallback_savings` names what the run can still change: fewer types for a comparison of types, and for single-type runs `--memory on` (memory both), the time model's `--jobs` (fewer) and fewer targets (several).

**ordo.py**, from the bank to the answer:
- `load_ordo_bank` reads `bank/ordo/` (format `probatio-ordo-1`), checks every file against the manifest pinned in ORDO_MANIFEST_SHA256, and derives the U and O worlds with v4's `derive_cell`. `check_ordo_bank` refuses a bank the planner cannot use.
- `plan` turns a selection into calls in v4's shape under the plan rules of SCORING.md 12: Class I in both frames (F1 role-free, F2 authority, the half fraction), the three-way items for the triangle, V12, the red flags, the errands (role-free, authority, and each named target's counterfactual worlds). Its `only=` filter is the private pilot plan's. `count_plan` prices any calls, ordo's or v4's, from `docs/ordo/budget.json["pricing"]`, the budget's one source.
- `score` reads the replies and records through v4's credit rule and report parser and builds the card: `pair_share` (π), `pair_index_r` (P^II), `authority_shares`, `relations` (the partial order), `standings`, `cycle_flag`, `named_effect`, the red flags (which no index reads) and V1 to V15. Intervals are v4's cluster bootstrap, widened for few clusters (`small_cluster`, PREREG.md Amendment 3, after Stage 0 found the plain percentile interval too narrow); the role-free errand rows widen through one named hook, `errand_interval` (`interval_rule`), with half their common tasks (PREREG.md Amendment 6, Stage 0b's candidate C), and `errand_rule_status` is the rule's completion gate over its evidence, `docs/ordo/errand_rule.json` (`docs/ordo/rule_evidence.py` writes it, and refuses what the gate would refuse). The gate reads the evidence's two artifacts itself: every cell of Stage 0b's acceptance against the frozen targets (`stage0b_problems`), and each allocation menu's minimax winner recomputed and matched to today's quick plan (`allocation_contents`). `rule_fingerprint` covers every function and constant those numbers depend on, traced from the scorers (`rule_dependencies`). The answer names a row too wide to rank at its tier; while the gate reads PENDING it names no role-free errand row and says why instead (`rule_pending_line`).
- `answer_table` and `svg` lead with the answer. When the run scored named targets, the names the user gave come first (`names_block`, `names_panel`): one row per name and class with the name's index, 0 to 100, beside its twin's (the roster's entity of its type measured the same way in its place) and Δ_T with its interval; then `names_notes`: what each shown class's number is (`class_leads`, one of `CLASS_LEADS` per class: Class I is a balanced share of choices, Class II 50 plus half the mean relative difference of the errand measures), each insufficient name with a plain line per opponent type (`insufficient_lines`, `opponent_lines`: what passed on its own, or not usable with the dropped parts by name, `PART_NAMES`), the position-driven gloss when a part was dropped for it, and at quick `quick_names_line`. Then the types, under `types_heading` (its entities per type, from `card["entities"]`, which `measured_entities` reads from run.json's rosters with `distinct_names`, the planner's own rule) with `types_sentence` (what the type indices are) directly under it, then one table of each pair's index around 50 and the ordering it supports, then the figure. Every heading, column and label names those entities through `roster_words`, which reads `card["roster"]` (`roster_kind`: "baseline" only when run.json's custom_controls is empty, since a custom control may be real; probatio's compare preflight asks the same words). Names in markdown pass `md` (escaping, defence in depth beside the name guard). report.md's "Named targets" adds a table per name and class of every component against every opponent (`named_component_lines`). `write_results` writes them into out/ordo/. The figure cuts every string a user supplied (a name, the model in the subtitle) to its budget with `fit`, by an upper bound on width (`text_px`, `char_em`: the widest Latin letters, non-Latin and full-width characters at 1 em), keeping the whole in a `<title>`; TestFigureInChrome measures the real boxes in headless Chrome.
- **What a named effect is made of** (card schema `probatio-ordo/3`). `named_class1` and `named_class2` return Δ_T and its interval only and are unchanged. `named_class1_levels` and `named_class2_levels` recompute, at the point and with the same helpers, what Δ_T is built from, and `named_effects` puts it under each effect's `levels`: `target_index` and `twin_index` (the mean over opponent types of each side's index, so their difference is Δ_T) and `per_opponent` (`class1_opponent`, `class2_opponent`: every component's two sides, kept or the guard's reason, and the pair's index pair when it has one). They feed no number the scorer prints; `assert_levels_match` in tests/test_ordo_scoring.py holds target_index - twin_index to Δ_T on shared fixtures.
- `recognition_plan`, `recognition_status` and `relabel`: V12's two calls per custom control, and the head's "reads as real" warning.
- `permutation_test` is the pilot's primary test (SCORING.md 11), which `docs/ordo/primary_test.py` states as a reference.

## Watching a run (live.py)

live.py, beside probatio.py, holds both views of a v4 run, and probatio imports it for every v4 run (`import_live`). Neither view writes anything in the results folder.

- **The live line.** `live_line` makes a `LiveLine` with the run's `--jobs` and tier (the line's first word), the prior rate of each call (the preflight's `expected_seconds` under the run's `run_profile`) and Claude Code's `QuotaLog`, whose `latest()` keeps the newest usage reading in memory. `run_calls` calls `begin`, `finished` for each call and `say` for its messages, and `close` ends it. In a terminal at least MIN_COLUMNS wide the line is redrawn in place, clipped by display columns (`columns`, `clip`: wide characters take two, combining and format characters none), each second and on every call; otherwise it prints a checkpoint at each tenth of the run and at the end, with no CR or escape. One lock covers every draw.
- **The page.** With `--watch`, `main_v4` and `main_compare` make one `Watch` for the command, which serves `VIEW_V4` through `serve_page` and has one tab per run (`tab_label`). `execute_run` (or main_v4's own path) starts each run's view with `watch_view`, which gives it the run facts (`run_facts`, nothing else of run.json), the entity names (`roster_names`) and the provisional scorer. After the run is scored it hands the final card over in memory (`Watch.finish`), and `hold_page` keeps the page up until Ctrl-C.
- **The observer.** `RunView` reads replies.jsonl through `CommittedLines` (only newline-committed dict lines with their required keys; it resets on a replaced, shrunk or rewritten file) and the newest task's records and reports (`Card`, `read_followup`, `folder_identity` for the attempt). When an errand's reply line lands, it captures the errand's `episode_facts` once, so every snapshot is frozen; a capture that fails waits in `retry` (by call key, with its record and attempt) and is read again at each refresh, and its record and facts enter the snapshot together once it succeeds. Every read is caught and shown as a fixed sentence with the exception's class only. `ViewRedactor` redacts every free-text field before it is cut, on calibration/redact.py's contract (tests/fixtures/redact_cases.json holds both to the same cases), and `redact_all` makes a last pass over /state. Which variables are secret-named is the page's own, narrower rule (`secret_named`: whole name parts, so GIT_AUTHOR_NAME, XAUTHORITY and SSH_AUTH_SOCK are not), since the --ui page refuses any word its redactor would change; `matched_names` says which variables a redaction matched, by name alone.
- **The provisional scorecard.** `Provisional` is one worker per run. Triggers coalesce, at most one scoring starts per PROVISIONAL_SECONDS, and the final card always wins. It scores a frozen snapshot with the final scorers over the full plan: `card_of` (score_run's scoring, split out of it, `private` and with `facts`) for v4, ordo's `score_units` over `units_of(..., facts)` at `card_tier`'s tier for a cross-type run. So a call not yet made is a missing unit, the fingerprint, seed and B are the final ones, and no file is read. `v4_rows` and `ordo_rows` turn a card into the page's rows (a cross-type card's named targets first, `name_rows`, with ordo's own words, cells and reasons: the class leads, the position-driven gloss, the quick-tier line and each insufficient name's per-opponent lines); a quick card leads with the scorecard's own line (QUICK_CARD_LINE, ordo's for a cross-type card), and a class the tier does not plan reads as the scorecard's row does (NOT_RUN_IN).

```mermaid
flowchart LR
  R["run_calls"] -->|"begin, finished, say, close"| LL["LiveLine (stderr)"]
  R -->|"appends"| F[("replies.jsonl, episodes/")]
  F -->|"CommittedLines, read_followup"| V["RunView"]
  V -->|"frozen snapshot: replies + episode_facts"| PW["Provisional: card_of or score_units"]
  S["score_run / ordo.score"] -->|"final card, in memory"| PW
  LL --> V
  V --> P["serve_page: 127.0.0.1, token, Host, CSP"]

```

## The --ui page (ui.py)

ui.py serves one page through live.py's `serve_page`, with the `--watch` page's hardening and four POST actions, each of which must carry the token in the X-Probatio-Token header as well, with no foreign Origin (CSRF). The page reads its defaults from probatio (`defaults`: parse_args_v4's own parser, and each type's rosters from `print_entities`). `build_command` is the one translation, pure: the form becomes an argv with only the options it changed (classes left at all three send no `--class`, and any subset is sent, even one equal to the tier's own classes), with a single-type run written as README writes it (`--target NAME`, after `--target-type TYPE` for an organization or a nation), so it takes v4's own path and shares a terminal's folders and run.json, and `--compare` with `--target TYPE=NAME` only when two or three types are compared (a person, the user or anyone, is the individual row's, so the page never writes `--name`: `--target NAME` plans the same run, item for item), `--entities results/ui-entities-<sha256>.json` for roster edits and `--watch` unless the page's watch choice is off, and either way the command built is the one checked and run, byte for byte; the words the page shows and Copy copies are `command_words`, each displayed, so a word longer than DISPLAY_CHARS or holding a character display escapes is shown and copied cut or escaped, and that copied command differs from the one Run starts. any other refusal the guard's own words under the row's label; a name is written in the guard's form, and one starting with - as `--target=NAME`, one word, by `target_words`); `required` is the one home of what a run needs before it can be checked (an agent; for a single-type run a name in that type's row; enough names in each roster list the form shows, `lists_shown`, below its `LIST_COUNTS` minimum being a missing piece and an over-full list probatio's to refuse; a refusal names the folder and the page's fix, `BLOCKED`), and only on a pass records an `Approval`: the argv, the snapshot's bytes and each run's plan fingerprint (`prepared`). `Session.run` starts only that approval, after reading the snapshot again, preparing the plan again and asking `resume_refusals` again inside the gate, just before the `Runner` starts in its own session, so a folder that took a run since Check refuses the Run, named as Check names it, with probatio's own words after the Check's preflight (the `Approval` keeps it).     B --> C["isolate.check (guard.py): no API key, no parent memory, clean dirs, contract, pinned build, token login"]
```mermaid
    C --> D["probatio.py --dry-run: memory list, model, jobs, planned calls"]
    D --> P["probatio.py in the room; STOP and the room checked before every launch"]
    P -->|"every claude / codex call"| W["shim.py: guard.py per call, rules re-applied, init / meter / model protocol, redact.py on every output, Codex home and cap"]
    W --> Q["scheduler.py: quota.jsonl here, the account ledger on the home host (account.py)"]
    Q -->|"newest reading of any host at a limit (default 0.60 / 0.60)"| R
```

`run.py` validates the spec (forwarded arguments by exact name only), fixes the run's fingerprint (every pinned executable resolved and hashed, world.py included, and checked again before every launch), builds the run's room (`isolate.py`) with its contract, checks it, checks probatio's dry run (memory list, model, jobs, planned calls), then runs probatio with the room's environment and its own flags (`--memory`, `--auto-memory off`, the registered `--effort`), checking for STOP and checking the room again before every launch. probatio finds the room's `claude` and `codex` first on its PATH. Those are wrappers around `shim.py`, which checks each call's own context against the room contract (`guard.py`), re-applies the rules (auto memory off, CLAUDE.md off in an off run and on in an on run, the pinned effort, no API key), refuses any option outside the exact command contract probatio uses (the only MCP server allowed is probatio's world.py, pinned by interpreter, path, sha256 and the run's episode folders), turns JSON into stream-json and checks it as a protocol (init with no API key and exactly the pinned build first, usable quota telemetry, exactly the registered model) before it accepts or releases a result, sends every output through the redactor (`redact.py`, which redacts a text whole before any cut), and checks each Codex call's home and reserves it against the Codex arm's cap of 1,000 charged requests. The scheduler (`scheduler.py`) decides pause and resume once for the whole subscription from the account's quota meter (`meter.py`), which keeps each window's high-water mark and reset so no partial, stale or reset-less reading can clear a hold: each host keeps its readings in `quota.jsonl` and publishes them to one ledger (`account.py`), a lock-protected file on its home host that other hosts reach over ssh. When the scheduler says pause, the shim refuses new calls, probatio stops after its error streak, and `run.py` sleeps until the window resets and reruns the same command, which resumes, but only once a post-reset five-hour reading is below 0.40. At seven-day 0.60 the study stops instead: the ledger latches the stop, and only an operator's release after Ephraiem's go (`account.py --release-study-stop`) lifts it. The stage caps count the burn as the summed positive increments of every reading, apart from the high-water marks that drive the pauses. `quota.py` holds the pause rules as pure functions. `calibration/README.md` has the details and the decisions still to confirm.

The v4 additions keep planning and scientific decisions separate from subject execution. `calibration/grid.py --codex-model <recorded-model> --dry-run` prints the registered A, B1, B2, Haiku and Codex schedule without a model call. `grid.py --out <fresh-folder>` writes runner specs and exact rendered memory audits from `calibration/ladder/*.md.tpl`; `ladder.py` owns their one-pass rendering and hashes. The pure `eligibility`, `stage_caps` and `cap_status` functions hold the rules for actual-time retests, stage order and the stage caps, and `stages.py` enforces them: `run.py` refuses a staged spec until `eligibility` finds it ready (from the plan, the plan's `control.json` attestations, the runs' records and B1's verdict computed by `analyze.py`) and opens its stage in the account ledger; before every launch, and in the shim before every charged call, `cap_status` checks the burn the ledger has summed since the stage opened, and a stage at its cap stops with STOP. The Codex arm's count is reserved in the same ledger, atomically.

`calibration/analyze.py` reads finished scorecards and metadata, validates provenance, excludes Stage A, and writes the pilot decisions plus `levels.svg`, its exact CSV and a description. `criteria.py` owns the tri-state decisions and the common-set comparisons (CALIBRATION 9: each run's own indices over the components sufficient in both, thresholds decided at stored precision); `stats.py` owns ICC(A,1), tied Spearman and paired retest resampling; `resampling.py` owns shared item/task resampling from `units.jsonl`. Missing observations and undefined intervals remain explicit. Read `calibration/STAGES.md` and `calibration/ANALYSIS.md` for the interfaces and limits, then the planted tests beside the existing calibration tests.

## Testing a change

`python3 -m unittest discover -s tests` and `python3 -m unittest discover -s calibration/tests` run every test; none calls a real agent. The bank's reproduction tests need the pinned datasets in .cache/ (`python3 tools/build_bank.py --out <a scratch folder>` downloads them once; without `--out` it rewrites bank/, bank/README.md's Provenance) and are skipped without them. A change to bank/src/ or the builder is followed by a rebuild, `tools/build_bank.py --check`, and a new BANK_MANIFEST_SHA256. A change to the bank format goes into BANK_FORMAT.md, the loader (`load_bank`, `check_bank`) and tests/fixtures/make_bank_small.py together; rerun that script afterwards, since a test refuses a stale bank_small/. render_cases.json is shared with the bank builder (INTERFACES 8), so a change to `entity` or `render` updates its cases rather than the tests alone. A change to anything scoring reads (a unit's fields, a threshold, a schema key) starts in SCORING.md or INTERFACES.md, and the schema's version changes with any field's meaning. For ordo: a change to bank/ordo/src/ or tools/build_ordo_bank.py is followed by `python3 tools/build_ordo_bank.py`, `--check`, and a new ORDO_MANIFEST_SHA256 in ordo.py; a change to a plan rule or a rate goes into docs/ordo/budget.py, then `python3 docs/ordo/budget.py --write`, and the count tests compare ordo.plan and the preflight with it. `docs/ordo/apply_ordo.sh` runs every check under the guard (stub CLIs, no keys, no network).
